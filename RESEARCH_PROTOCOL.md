# Протокол исследования v1 — 2026-09-25

Цель: сравнить расход ресурсов ненагруженного и слабонагруженного Spring Boot-сервиса при одинаковой полезной работе. Задержки, ошибки и завершение фоновой обработки — обязательные ограничения.

## Матрица

| Runtime | Основной профиль | Отдельный контроль |
|---|---|---|
| HotSpot / Liberica | `work-hotspot-elastic`, Xms32m / Xmx512m | `work-hotspot-fixed`, Xms=Xmx512m |
| OpenJ9 / Semeru | `work-openj9-elastic`, Xms32m / Xmx512m | `work-openj9-fixed`, Xms=Xmx512m |
| GraalVM JIT | `work-graalvm-elastic`, Xms32m / Xmx512m | `work-graalvm-fixed`, Xms=Xmx512m |
| GraalVM Native Image | `work-graalvm-native`, настройки heap по умолчанию | нет fixed JVM heap |

Внешний бюджет приложения: **2 CPU / 1 GiB, без swap**, одна реплика. MongoDB, Kafka и WireMock работают отдельно и сохраняются во всех сценариях. Сравниваются дистрибутивы и модели исполнения; различия ОС, JDK и GC не позволяют приписывать всё отличие только JIT/AOT. GC и флаги внутри серии не менять; сохранять фактические версии и image IDs.

## Сценарии

| Сценарий | Полезная нагрузка | Начальная длительность |
|---|---|---|
| Fresh idle | пустая БД, без seed и бизнес-запросов | 30 минут |
| Редкие запросы | `RATE=1 RATE_TIME_UNIT=10s` | 30 минут |
| Low load | `RATE=1 RATE_TIME_UNIT=1s` | 30 минут |
| Дополнительная нагрузка | `RATE=10 RATE_TIME_UNIT=1s` | отдельная серия |
| Post-load idle | тот же процесс после завершения фоновой работы | 30 минут |

Общий пул — 1000 заявок, `ORDER_POOL=1000 SEED_ORDERS=1000` задавать явно. Фазы: startup → preparation → load/low-load → drain → post-load-idle → finished; fresh idle: startup → preparation → idle → finished. Drain — до 300 секунд. Seed исключён из business latency. Фоновые задачи, MongoDB, Kafka и внешние вызовы включены.

Два независимых профиля:

- `normal`: SLOW 15% (1200 мс), остальные OK; без искусственных ошибок. Основная серия.
- `faults`: LONG_DELAY 3%, ERROR 5%, BAD_RESPONSE 2%, SLOW 15%, Mongo conflict 2%, Kafka duplicates 5%. Проверка устойчивости отдельно от основной серии.

Это доли детерминированных hash-бакетов, точные количества определяет trace. Внешний режим привязан к ID и точке вызова; отказы выбранных заявок устойчивы. Trace v1: seed `20260925`, заявка и результат по глобальному номеру итерации, независимо от VU. Сохранять trace и SHA-256. Внешние режимы и объём фактической фоновой работы должны совпадать у сравниваемых прогонов.

## Критерии допуска

| Профиль | Business p95 | Business p99 | HTTP / неожиданные ошибки |
|---|---|---|---|
| normal | <1500 мс | <2000 мс | 0 |
| faults | <2500 мс | <3000 мс | 0 |

Это инженерные SLO стенда, не SLA продукта. Не менять пороги по результату отдельной JVM. Ожидаемые искусственные отказы должны точно совпасть с trace; HTTP 200 с FAILED не считается успехом обычного запроса.

Ровно запланированное число бизнес-запросов; dropped=0. Допускается один отдельно учтённый пустой tick k6 на конечной границе trace: `iterations = planned + trace_boundary_skips`, skips ∈ {0,1}. Он не вызывает HTTP и не входит в latency. Другие пропуски и лишние запросы отклоняют прогон.

После drain: outbox пуст, все логические события опубликованы и обработаны, дубли сбалансированы, lag обоих Kafka topics=0; scheduler работал без неожиданных ошибок. Нет OOM, swap, рестартов, роста количества заявок и превышения границ состояния. Недостающие обязательные данные отклоняют прогон.

## Метрики и сравнение

Собирать working set Docker, полный расход/пик cgroup, OOM и swap; heap used/committed/max и доступные GC-счётчики; накопленное CPU time и throttling; интенсивность, latency, раздельные ошибки и состояние фоновой обработки. Определения, единицы и окна: [RESULTS_SCHEMA.md](RESULTS_SCHEMA.md).

Память сравнивать по одинаковым фазам и временным окнам. Working set не называть RSS. CPU считать разностями накопленных счётчиков. Не усреднять перцентили разных запусков. Сопоставлять только допущенные прогоны с совпадающими условиями, trace и фактической работой; низкая память при нарушении SLO не является преимуществом.

Перед baseline: correctness/smoke → pilot 10–30 минут → stability 1–3 часа → выбор длительности baseline. Сначала признать корректным HotSpot baseline, затем OpenJ9, GraalVM JIT и Native; не запускать полную исследовательскую матрицу заранее. Короткий smoke четырёх runtime проверяет исполнимость и не является baseline.

Для baseline: зафиксировать хост и образы, минимум 3 независимых повтора основных сценариев; новый процесс, MongoDB и Kafka между повторами. При сравнительной серии чередовать порядок runtime. p99 на 180 редких запросах статистически неустойчив; не делать из него вывод о хвостах большого потока. Главные выводы подтвердить повторными запусками.
