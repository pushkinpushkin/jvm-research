# Протокол исследования v1 — 25.09.2026

Цель: сравнить расход памяти ненагруженного и слабонагруженного enterprise Spring Boot-сервиса при одинаковой полезной работе. Задержки, ошибки и завершение фоновой обработки — обязательные ограничения, а не второстепенные показатели.

## Матрица

| Вариант | Основная серия | Отдельный контроль | Внешний бюджет приложения |
|---|---|---|---|
| HotSpot / Liberica | `work-hotspot-elastic`: Xms32m / Xmx512m | `work-hotspot-fixed`: Xms512m / Xmx512m | 2 CPU / 1 GiB, без swap |
| OpenJ9 / Semeru | `work-openj9-elastic`: Xms32m / Xmx512m | `work-openj9-fixed`: Xms512m / Xmx512m | тот же |
| GraalVM JIT | `work-graalvm-elastic`: Xms32m / Xmx512m | `work-graalvm-fixed`: Xms512m / Xmx512m | тот же |
| GraalVM Native Image | `work-graalvm-native`: настройки heap по умолчанию | отдельного fixed JVM heap нет | тот же |

Это сравнение готовых дистрибутивов и моделей исполнения. У Native другой GC и внутренний бюджет heap; одинаков только внешний бюджет. Разные ОС образов и patch-версии JDK не позволяют приписывать всё отличие только компилятору. GC не менять внутри серии; записывать фактическую конфигурацию, image ID, run-info и commit.

## Сценарии и нагрузка

- Fresh idle: новый процесс, пустая БД, без seed и бизнес-запросов; 30 минут наблюдения.
- Редкие запросы: `RATE=1 RATE_TIME_UNIT=10s`, 30 минут.
- Low load: `RATE=1 RATE_TIME_UNIT=1s`, 30 минут.
- RATE=10 — дополнительная серия и проверка работоспособности, не основной вывод исследования.
- После нагрузки: завершение фоновой обработки (до 300 секунд), затем 30 минут простоя того же процесса. MongoDB, Kafka, внешние вызовы и schedulers остаются включёнными.
- Общий пул: 1000 заявок; seed=1000. По умолчанию runner совместим с прежним пулом 10000: для серии явно задавать 1000 одинаково всем вариантам.
- Trace v1 задаёт заявку и ожидаемый результат для каждого глобального номера итерации. Seed `20260925`, содержимое и SHA-256 сохраняются. Изменение VU не меняет trace.
- `normal`: 15% SLOW (1200 мс по детерминированному hash), остальные OK; нет искусственных ошибок.
- `faults`: отдельная серия; LONG_DELAY 3%, ERROR 5%, BAD_RESPONSE 2%, SLOW 15%, синтетический Mongo conflict 2%, Kafka duplicates 5%. Это доли hash-бакетов, точные количества конкретного trace могут отличаться от процентов.
- Внешний режим привязан к ID и точке вызова. Это устойчивые сбои выбранных заявок, не случайные кратковременные сетевые сбои. Schedulers могут выполнять разное число действий при другом порядке завершения запросов: сравнение дополнительно разделяется по фактически выполненной фоновой работе и распределению внешних режимов.

## Критерии допуска (зафиксированы до эталонной серии)

Предложенные инженерные SLO: normal — p95 <1500 мс, p99 <2000 мс; faults — p95 <2500 мс, p99 <3000 мс. Это критерии данного стенда, не SLA банковского продукта. Не изменять пороги после просмотра результата одной JVM.

В обоих профилях: HTTP-ошибок 0, неожиданных бизнес-результатов 0, неожиданных исключений scheduler/consumer/outbox 0. Искусственные отказы должны точно совпасть с ожиданием trace. HTTP 200 с FAILED учитывается как ожидаемый отказ только для соответствующей итерации.

Ровно запланированное число завершённых итераций и бизнес-запросов, dropped=0. Незавершённые итерации обнаруживаются по несоответствию количества. После drain: исходящая очередь пуста, все логические события опубликованы и обработаны, доставка с дублями сбалансирована, lag обоих Kafka topics равен 0. Нет OOM, swap, рестартов и превышения границ данных. Недостающие обязательные метрики означают отклонение.

`validation.json`: `eligible=true` / «пригоден для сравнения» либо конкретные причины отклонения. Это допуск одного прогона; сравнивать разрешено только совпадающие общие условия и объём выполненной работы. Короткий smoke не становится эталонным исследованием от успешной валидации.

## Фазы и измерения

`startup → preparation → load/low-load → drain → post-load-idle → finished`; для fresh idle: `startup → preparation → idle → finished`.

Seed выполняется до запуска k6. Startup: от Docker StartedAt до readiness UP; readiness проверяется каждые 250 мс после готовности зависимостей. Подготовка данных, startup, drain и post-load idle не смешиваются с load-memory и business-latency.

Каждые 5 секунд: cgroup v2 current, inactive_file, lifetime peak, swap, OOM, CPU usage/throttling; Prometheus heap used/committed/max и доступные GC-счётчики; состояние ограничений и обработки событий. Working set = current − inactive_file (правило Docker). Это не RSS Java-процесса. CPU time и throttling — разности накопленных счётчиков, не сумма процентов CPU.

`phase-summary.json`: отдельные фазы и окна 0–60, 60–300, 300–600, 600–1200, 1200–1800, 1800–3600 секунд. Средняя память взвешена по времени (трапеции); медиана и максимум — по наблюдаемым отсчётам. Неполное окно помечено фактической длительностью; значения за пределами наблюдения не экстраполируются. `memory.peak` — полный накопленный пик cgroup, не пик working set отдельной фазы. Не усреднять перцентили разных запусков.

**Ограничения измерителя:** нужен Linux cgroup v2 с memory.peak; отсутствие обязательного поля отклоняет прогон. Текущий переносимый сборщик читает cgroup через короткий `docker exec`; память/CPU процесса чтения входят в измеряемый контейнер, Prometheus и `/research/state` также создают нагрузку. До эталонной серии нужен контроль влияния измерителя (например, интервалы 5 и 15 секунд). Малые различия ниже его влияния не интерпретировать как победу runtime. Kernel peak сохраняет пропущенные между отсчётами пики полного расхода памяти; sampled startup working-set peak не гарантирован, особенно у Native.

## Ограничения прикладной модели

Одна реплика приложения. Все изменения заявки синхронизированы ограниченным массивом из 1024 locks; scheduler перечитывает документ внутри lock. Это влияет на конкуренцию и входит в общую модель всех runtime. Масштабирование на несколько реплик требует отдельного решения конкурентных записей.

История ≤40; сохранённые receipts ≤1024 на заявку; cache ≤10000 IDs с TTL 1 час; outbox ≤256 на заявку, переполнение вызывает ошибку вместо удаления событий. Dedup гарантируется в пределах сохранённых receipts/cache, не для произвольного воспроизведения старого Kafka log. Событие и изменение заявки сохраняются атомарно в одном Mongo-документе; dispatcher удаляет событие только после broker ACK. Повтор после сбоя безопасен в пределах окна дедупликации. Неуспешная обработка не подтверждает Kafka offset; постоянная ошибка удержит lag и отклонит прогон. Retry failed orders действительно повторяет HTTP business flow, до 3 суммарных FNS attempts.

## Порядок допуска к эталонной серии

1. Java/Python tests, проверка всех 10 WireMock mappings, smoke всех четырёх runtime и fault-profile.
2. 30-минутный пробный прогон каждого runtime; проверить сырые данные, ограничения, observer overhead и SLO. До этого готовность длительной серии не подтверждена.
3. Зафиксировать хост, образы и настройки; минимум 3 независимых повтора каждого сценария. Между повторами новый процесс, Mongo и Kafka; порядок runtime чередовать.
4. Для вывода использовать только допущенные и сопоставимые прогоны. p99 на 180 редких запросах описателен и статистически неустойчив; не делать из него вывод о хвостах большого потока.
