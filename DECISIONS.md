# Существенные решения

## D-001: Elastic heap — основной профиль

Решение: Xms32m/Xmx512m для трёх JVM при внешних 2 CPU/1 GiB.
Причина: основной вопрос — память слабонагруженного сервиса; фиксированный Xms меняет исходный footprint.
Контроль: отдельный Xms=Xmx512m; у Native штатный heap под тем же внешним бюджетом.
Дата: 2026-09-25.

## D-002: Детерминированная работа и отдельные искусственные отказы

Решение: общий trace по глобальному индексу k6, seed и SHA-256; normal и faults раздельно.
Причина: распределение VU и случайный выбор не должны менять полезную работу.
Контроль: точные количества запросов/режимов/результатов, dropped=0, совпадение фоновой работы. Единственный endpoint tick допускается как измеренный no-op; HTTP-счётчики не ослабляются.
Дата: 2026-09-25.

## D-003: Ограниченная однорепличная модель доставки

Решение: 1024 striped locks; история ≤40, receipts ≤1024 на заявку, cache ≤10000 с TTL 1 час, outbox ≤256 на заявку. Переполнение outbox вызывает ошибку, а не удаление событий.
Причина: ограничить состояние и устранить конкурентное перетирание документов в одной реплике. Изменение заявки, receipt и outbox сохраняются одним Mongo-документом; outbox удаляется после broker ACK, Kafka offset подтверждается после успешной обработки.
Контроль: retry после Mongo/ACK failure, баланс логических событий/дублей, lag=0. Произвольный replay за пределами receipts/cache и несколько реплик не входят в гарантию; постоянная ошибка оставляет lag и отклоняет прогон. Failed orders повторяют реальный flow до 3 суммарных FNS attempts.
Дата: 2026-09-25.

## D-004: Раздельные фазы и влияние измерителя

Решение: startup/preparation/load/drain/post-load-idle считаются отдельно; seed исключён из latency. Используется cgroup v2 и переносимый docker-exec collector.
Причина: подготовка и фоновая работа не должны маскировать память и latency нагрузки; данные cgroup учитывают весь контейнер.
Контроль: raw-пересчёт, обязательные поля и покрытие окон; до baseline сравнить sampling 5 и 15 секунд. Сам docker exec и telemetry создают расход ресурсов; sampled peak не заменяет kernel peak.
Дата: 2026-09-25.

## D-005: Короткий checkpoint вместо истории переписки

Решение: пять канонических документов; в начале читать protocol/state, затем адресные данные. Порядок: correctness → pilot → stability → HotSpot baseline → остальные runtime → comparison → deep dives → validation.
Причина: экономить повторное чтение, сохраняя проверку гипотез и воспроизводимость.
Контроль: доказательства с commit/run ID, актуальный backlog, повторный аудит только по релевантному изменению. Smoke всех runtime остаётся функциональной проверкой.
Дата: 2026-09-25.

## D-006: Kafka lag admission берётся из Kafka CLI

Решение: обязательный lag для admission — `kafka-consumer-groups --describe` в `kafka-lag.txt`; Prometheus Kafka lag labels остаются дополнительной telemetry и не участвуют в допуске.
Причина: набор Prometheus labels для Kafka lag зависит от экспортера/версии и может предупреждать об отсутствующих или несовпадающих labels, тогда как CLI показывает фактический lag consumer group по двум topics стенда.
Контроль: валидатор fail-closed требует строки по `order.status.changed` и `business.event.occurred`, числовой lag и сумму 0; отсутствие Prometheus lag labels не означает нулевой lag.
Дата: 2026-09-26.

## D-007: Malformed cgroup sample не останавливает серию

Решение: collector пропускает пустые и malformed строки cgroup, используя первые два
токена валидной строки; samples с недоступными обязательными counters остаются
fail-closed, но raw и ошибка сохраняются в `cgroup-errors/`.
Причина: формат отдельных строк cgroup может отличаться на VPS/kernel без потери
базовых counters; часовой прогон не должен падать из-за одной такой строки.
Контроль: regression test на malformed raw, предупреждение в stderr и отдельный
артефакт ошибки для диагностики.
Дата: 2026-09-27.
